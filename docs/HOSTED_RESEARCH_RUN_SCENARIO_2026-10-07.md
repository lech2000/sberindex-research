# Полный прогон исследований СберИндекса в Фиксаре

Основной пользовательский путь — исполнение на нашей базе. Пользователь приносит данные и выбирает исследовательскую задачу; Фиксар принимает файл, запускает закреплённую версию метода и возвращает результат в дело. Репозиторий нужен для разработки методов и самостоятельного исполнения, а не как обязательная ступень пользовательского входа.

## Состояние подключения 07.10.2026

После поручения владельца подготовлена первая реализация: частная очередь с семидневным результатом, обучение сезонной Ridge/Ridge AR и кластеризация K-means/Ward на пользовательском файле. Код aiOS2 `629817a81`; до Linux-проверки и выкладки это не подтверждение доступности в проде. Реализация выделена в самостоятельный запуск, пока без материалов дела. Целевой сценарий ниже сохраняется для следующего этапа.

## Предшествующий доступный режим

Проверено 07.10.2026 по коду aiOS2 `5984e3b4243eb9e5c51862f09ed2411eb95a3d7a`, KB62 №16530 и №17066, исходникам публичной формы из научного коммита `8a8d2b92b4a9dd161d0d8aa34ec21ff0ffdde5b5`. Это описание подтверждённых возможностей, а не отчёт о выполнении нового научного эксперимента.

Вебформа принимает CSV/XLSX/Parquet после входа в Фиксар. Серверный инструмент считает статистику, группировки, корреляции, ошибки уже готовых прогнозов и сверку выпусков. Пользователь скачивает JSON с формулой и квитанцией. Файл не сохраняется в дело, очередь отсутствует, форму нельзя считать полным запуском исследовательского репозитория. Пользовательская инструкция: [Как исследовать свои данные](USER_DATASET_GUIDE_RU.md).

## Целевой сценарий полного исследования

Анна получила новый месячный выпуск муниципальных расходов и хочет узнать, изменились ли профили территорий и точность прогнозов. Она открывает Фиксар, выбирает «Исследовать данные СберИндекса» и прикладывает файл. Платформа предлагает уточнить период, единицы измерения и идентификаторы территорий, показывает пропуски и отличия от прежнего выпуска.

Анна выбирает Атлас для сравнения структуры расходов или Радар для прогноза и отклонений. Она видит подходящие для её данных методы, размер выборки, параметры, ограничения, оценку времени и стоимости. Неподходящий метод объясняет, каких данных не хватает. Кнопка «Запустить исследование» подтверждает конкретный прогон; до этого вычисление не начинается.

Фиксар создаёт задание в её деле. Статусы понятны: «Проверяем данные», «Выполняем расчёт», «Готовим отчёт», «Готово» или «Нужны уточнения». Пользователь может закрыть вкладку и вернуться в дело; остановка задания должна быть отдельным действием. После завершения он получает таблицы, графики, объяснение, ограничения и архив воспроизведения. Повтор с теми же данными и настройками создаёт новый прогон; сравнение с обновлённым файлом показывает различия.

Этот сценарий требует реализации и не представлен на лендингах как доступная функция.

## Первая версия полного исполнения

Начать с одного небольшого, заранее проверенного пути: новая таблица расходов → паспорт данных → группировка по категориям и территориям → выбранный простой сезонный прогноз → сравнение с базой на общей маске → отчёт. Кластеризацию Атласа подключать отдельным следующим методом с явными требованиями к долям, периоду и полноте панели. Набор методов расширять после проверки реального пользовательского прогона, а не одновременно переносить все исследовательские скрипты.

Для каждого разрешённого метода нужен фиксированный контракт входа, набора параметров, результатов и ограничений. Метод и версия кода закрепляются до запуска; обучение использует только разрешённую историю. Просмотренные ретроспективные данные не переименовываются в независимый будущий тест.

## Что нужно добавить в платформу

1. **Сохранённый вход в деле.** Использовать штатную загрузку материала с проверкой доступа владельца. У каждого выпуска — отдельный материал, контрольная сумма и паспорт; исходный эталон остаётся неизменным.
2. **Реестр методов.** Закреплённый код и зависимости, допустимые параметры и критерии применимости. Текущие инструменты работают с именованными историческими наборами; для чужого файла нужна отдельная проверенная привязка. Произвольный пользовательский Python не включать в первый режим.
3. **Задание на исполнение.** Отдельный worker в инфраструктуре Incus/Docker, квоты CPU/памяти/времени и независимый каталог каждого запуска. Получает разрешённый материал и конфигурацию метода, а не произвольный серверный путь. Повтор запроса не должен создавать два платных задания.
4. **Проверка результата.** Числа считает код метода; объяснение строится из результатов. Пропуски, общая маска сравнения, происхождение данных и доступность во времени показываются вместе с выводами. Неудачный метод и отрицательный исход тоже сохраняются.
5. **Возврат в дело.** Права на просмотр, статус, отмена, журналы ошибки, отчёт и архив доступны владельцу и явно приглашённым участникам. Пользователь сам решает, публиковать ли результат.

Для сохранения воспроизводимости квитанция полного прогона должна связывать файл и его паспорт, код и зависимости, параметры, выбранные периоды, seed, фактическую выборку, результаты и время исполнения. Нынешняя квитанция предварительного расчёта покрывает более узкий объём и не заменяет такой manifest.

## Критерий готовности

Один пользователь с доступом к своему делу загружает файл, подтверждает параметры, получает расчёт, закрывает вкладку и повторно открывает тот же результат. Чужой аккаунт его не видит. Повтор воспроизводит числа; новый выпуск создаёт отдельное задание; отмена и превышение лимита заканчиваются понятным статусом. Неподдержанный метод не подменяется описательной статистикой. После этого сценарий можно обозначить на лендинге как полный запуск исследования.

Изменения исполняемого кода платформы должны пройти fixar-devops/F7b и обычную дисциплину выкладки. Первая реализация worker и ограниченных методов подготовлена отдельно; сохранённые материалы дела, полный реестр научных методов и сравнение двух сохранённых исследовательских прогонов остаются следующим этапом.
