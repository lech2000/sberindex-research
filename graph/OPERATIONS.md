# Смотритель муниципального графа: эксплуатационный контракт

Дата: 20.09.2026. Дело FixAR: `case_43de12a8dc2e4abd`. Staging-корпус KB-Forge: `77`.
Дело куратора: `case_d058db85c48a487c`.

## Назначение

Смотритель круглосуточно пополняет доказательную модель для двух конкурсных
исследований. Он не строит «тайную социальную сеть пользователей». В графе
есть муниципалитеты, организации, источники, наборы, показатели, события и
явно помеченные синтетические участники. Зарегистрированный пользователь
становится вершиной только по отдельному разрешённому продуктовому событию;
исследовательский обход публичного веба такого события не создаёт.

Один запуск обрабатывает одну тему или один официальный источник. Результат
сначала попадает в корпус 77 как staging-доказательство. Публикация в будущую
графовую БД будет отдельной детерминированной операцией после проверки схемы,
идентичности и происхождения.

## Слои и происхождение

1. **Observed** — строка неизменённого файла или факт официального реестра.
2. **Source estimate** — оценка, опубликованная источником; хранится с его
   методикой, периодом и vintage.
3. **Model estimate** — наш расчёт из зафиксированного run и входных SHA-256.
4. **Synthetic assumption** — участник или связь сценария. Она не повышается
   до observed ни повторением, ни высокой вероятностью.

Временные поля разделяются: `observed_at`, `published_at`, `available_at`,
`valid_from/valid_to`, `checked_at` и `vintage`. Конфликтующие значения не
перезаписываются: создаётся новая версия с собственным источником.

## Лестница одного запуска

1. Найти существующие сведения в корпусах 74–77 и в каталоге загруженных
   таблиц.
2. Сформулировать один недостающий атомарный факт: идентичность МО, источник
   показателя, организация в МО, административное изменение или событие.
3. Проверить бесплатный путь: встроенный поиск MiMo Pro, официальный API/файл,
   Jina и robots-aware чтение.
4. Пассивный Recon применять только после allowlist. Apify применять только
   для сложного публичного JS-сайта, если предыдущие пути не закрыли пробел.
5. Вернуть ровно один `EVIDENCE_JSON … END_EVIDENCE_JSON` по
   `evidence.schema.json`. n8n проверяет размеры, URL, время, ссылки сущностей,
   классы происхождения и совпадение `run_key`.
6. Валидный блок идемпотентно интегрируется в корпус 77. Ошибка формы не
   записывается; `blocked` записывается как проверенный блокер без фиктивных
   вершин и связей.
7. После ingest отдельный `sberindex_research_curator@2` сверяет evidence с
   лестницами A/R/G, принимает или отклоняет claims и формулирует ровно один
   следующий атомарный шаг. Его `CURATOR_JSON` проходит отдельную схему и
   записывается в тот же корпус как решение, а не как новое наблюдение.

## Круглосуточная очередь

n8n запускает один проход каждый час со смещением семь минут. Очередь
циклическая: словарь муниципалитетов СберИндекса; ОКТМО Росстата; БДМО 8423005;
метаданные расходов; метаданные мобильности; административные изменения.
Ключ расписания стабилен для темы в пределах суток: повторный запуск получает
тот же `client_message_id`, а KB-Forge дедуплицирует тот же документ по SHA-256.

Живой исследователь может попросить Atlas/Radar-агента поставить отдельную
тему через `sberindex_research_request_run`. URL workflow и номер корпуса
модель выбрать не может. `sberindex_research_repair` перечитывает каталог и
проверяет три закреплённые поверхности агентов. Для изменения кода сохраняется
контур `fixar-devops`: bounded blueprint/diff, проверка и человеческое
принятие; произвольного shell из диалога нет.

Atlas и Radar перед новым ходом читают решения куратора через закреплённый
`sberindex_directive_kb_search`, который видит только корпус 77. Куратор не
запускает агентов и не ставит следующий workflow сам: это разрывает
рекурсивный цикл. Его `next_topic` подхватывается живым исследователем либо
следующим плановым проходом после явного правила оркестрации.

## Ворота перехода к графовой БД

- G0: схема и четыре класса происхождения соблюдаются на 100 тестовых записях.
- G1: кроссволк имеет источник, checksum, vintage, долю однозначных и список
  неоднозначных/неприсоединившихся ID.
- G2: повторный ingest не создаёт вторую сущность или связь.
- G3: конфликт двух vintages сохраняется как две версии.
- G4: синтетические сущности исключены из метрик по умолчанию.
- G5: на одинаковом тесте измерена добавочная польза графовых признаков против
  M0 без графа. Без улучшения граф остаётся объяснительным слоем.
